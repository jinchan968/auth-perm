# 代理协作规范

本文档结合 Claude folder 的常见组织思路，以及近期更常见的 harness agent / 多代理协作方式，约束当前仓库中的任务拆分、上下文交接和验收方式；

## 1. 核心思想

### 1.1 共享规则短、长说明下沉
参考 Claude folder 的实践，代理规则最好分成两层：

- **共享入口**：`./AGENTS.md`
  - 只保留高频、稳定、必须遵守的规则；
  - 控制篇幅，避免一次把所有背景都塞进上下文；
  - 提供明确索引，让代理先知道“应该去哪里读详细说明”。
- **详细专题**：`./docs/*.md`
  - 分别承载架构、开发、协作流程、专题实现说明；
  - 便于独立维护，也能减少根规则文件的上下文噪音。
- **本地偏好**：`./AGENTS.local.md`
  - 放本机、本人、隐私相关约束；
  - 不把机器差异、私有凭据、个人偏好混进团队共享规则。

### 1.2 把代理当成一条流水线，而不是一个万能角色
更接近 harness agent 的实践，是把复杂任务拆成多个阶段，而不是让单个代理一口气从需求跳到实现：

1. **Planner**：理解需求、识别影响面、规划步骤。
2. **Implementer**：按计划改动代码或文档。
3. **Reviewer / Verifier**：检查漏项、运行验证、确认交付完整。

即使实际执行时还是一个代理串行完成，也应该按这三个视角思考，避免直接“看见问题就写代码”。

## 2. 角色分工

### 2.1 Planner
适用场景：
- 需求跨后端 / 前端 / 权限 / 租户多个模块。
- 需要判断影响范围和优先级。
- 需要先整理文档结构、任务方案或迁移路径。

Planner 的输出至少应包含：
- 目标与边界；
- 涉及文件 / 目录；
- 风险点与依赖关系；
- 推荐执行顺序；
- 最低验证清单。

### 2.2 Implementer
适用场景：
- 已明确改动范围，进入具体实现或文档更新阶段。

Implementer 的要求：
- 只在确认过职责边界后动手；
- 保持改动尽量聚焦，避免顺手重构无关内容；
- 对新增能力同步补齐注册、类型、路由、权限、文档、测试；
- 避免往 handler / route / page 塞业务逻辑。

### 2.3 Reviewer / Verifier
适用场景：
- 实现后做回看、查漏补缺、跑验证。

Reviewer 的重点：
- 是否漏了 `container`、`module.go`、`route.go`、`ui/lib/api`、`ui/types`、权限显隐等同步点；
- 是否有越层依赖；
- 是否补了必要文档；
- 是否运行了匹配改动范围的验证命令。

## 3. 任务拆分原则

### 3.1 按边界拆，不按文件数拆
优先按“能力边界”而不是“编辑多少文件”来拆任务：
- 后端接口设计与装配；
- 前端 API / hook / 页面消费；
- 权限资源与显隐；
- 文档与测试。

### 3.2 先定义契约，再做两端实现
对于全栈任务，推荐顺序：
1. 明确 API 契约、字段、错误语义、权限要求。
2. 实现后端接口。
3. 封装前端 API。
4. 修改 hook / store / 页面 / 组件。
5. 回补测试与文档。

### 3.3 可并行的只有“读”和“互不冲突的子任务”
可以并行：
- 同时阅读多个候选文件；
- 一个代理梳理后端影响面，另一个代理梳理前端影响面；
- 文档整理与代码阅读并行。

不要并行：
- 编辑同一个文件；
- 编辑强依赖前一步结果的任务；
- 在 API 契约未定前，同时推进两端实现。

## 4. 上下文交接模板
复杂任务在阶段间交接时，至少应带上以下信息：

### 4.1 目标
- 本次要完成什么。
- 明确不做什么，防止范围蔓延。

### 4.2 影响范围
- 涉及的目录或模块。
- 关键文件入口。
- 需要同步的上下游。

### 4.3 风险与注意事项
- 是否涉及认证、权限、租户。
- 是否有迁移、缓存、调度器、会话失效等副作用。
- 是否已有历史专题文档需要同步。

### 4.4 验证要求
- 至少跑哪些命令。
- 是否需要手工验证页面或接口。
- 哪些测试是阻塞项。

## 5. 本项目的任务路由建议

### 5.1 后端任务
优先查看：
- `./docs/ARCHITECTURE.md`
- `./internal/container/`
- `./internal/controller/http/route.go`
- 对应领域模块 `module.go`、`service/`、`repo/`、`handler/`

适合单独拆出的子任务：
- 路由 / handler 增补；
- 领域服务与 repo 调整；
- 中间件与权限校验；
- 测试补齐。

### 5.2 前端任务
优先查看：
- `./docs/ARCHITECTURE.md`
- `./docs/DEVELOPMENT.md`
- `./ui/lib/api/`
- `./ui/hooks/`
- `./ui/types/`
- `./ui/app/` 与对应组件目录

适合单独拆出的子任务：
- API 客户端封装；
- hook / store 状态逻辑；
- 页面与组件改动；
- 权限显隐回归。

### 5.3 全栈任务
最推荐的拆分方式：
1. 契约与影响面梳理；
2. 后端接口与注册；
3. 前端 API / hook / 组件；
4. 权限资源同步；
5. 文档与验证。

特别是认证、权限、租户任务，不建议把后端和前端改动完全分离到两个互不沟通的实现者手里；必须共享同一份契约和资源标识表。

## 6. 文档协作规则
1. 长规则不直接塞进 `AGENTS.md`，而是下沉到 `docs/`。
2. 新增长文档后，要回到 `AGENTS.md` 加索引。
3. 一次性排障文档可以留在 `docs/` 根目录；若后续被多次引用，应提炼为长期规范并迁入核心文档。

## 7. Definition of Done
以下清单满足后，任务才算真正完成：

- [ ] 需求范围明确，没有遗漏关键上下游。
- [ ] 改动遵守后端 / 前端分层边界。
- [ ] 认证、权限、租户相关改动已同步检查前后端契约。
- [ ] 必要的注册点、类型定义、权限资源标识、文档已补齐。
- [ ] 已运行与改动范围匹配的构建 / lint / type-check / 测试。
- [ ] 没有新增调试式输出。
- [ ] `AGENTS.md` 与 `docs/` 的索引关系保持最新。

## 8. 什么时候必须停下来先提问
虽然默认应尽量自主推进，但以下情况建议先确认：
- 需求本身存在多个互斥方向；
- 会影响外部 API 契约但没有现成上下文；
- 可能引入破坏性迁移或删改大量历史行为；
- 业务命名、权限资源命名缺少明确规则，且仓库内没有稳定先例。

其余多数情况下，优先通过阅读相邻文件、现有实现和已有文档自行收敛答案。
